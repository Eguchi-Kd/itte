## 0. この文書の使い方（Claude Code 向け）

この文書は、Claude Code がこれだけを読んで実装を完了できるように書いている。4つの設計書の内容は、矛盾を解消したうえでこの文書にすべて取り込んである。元の4文書は参照しなくてよい。

### 0.1 正本の優先順位

記述が食い違って見える場合は、次の順で優先する。

1. **§2.3「絶対制約」**と**§7.4「不変条件」**
2. **§12「受け入れ基準」**
3. §7〜§8（データモデル・ドメインロジック）
4. §6（画面仕様）
5. その他の章（意図と背景の説明）

### 0.2 作るもの

- 単一ユーザー向けの日本語 PWA。**サーバー・ログイン・外部通信はない**。データは端末内の IndexedDB にだけ保存する。
- 4つのモジュール（習慣・着手・盤面・段）を1つのアプリに統合する。共通のホーム「きょうの道」、共通の週次ふりかえり、共通の実験ランナーで束ねる。
- UX は **Duolingo の操作感**（1タップ、短い区切り、次にやることが常に1つ光っている、即時の手応え）を移植する。ただし **採点・ストリーク・XP・リーグ・祝福演出・催促通知は作らない**（§4 で理由と代替を定義）。

### 0.3 作業の進め方

1. §13「実装順序」のタスクを番号順に実装する。1タスク＝1コミット。コミットメッセージは `feat(T07): 習慣作成ウィザード` の形式にする。
2. 各タスクの終わりに `npm run lint && npm run typecheck && npm run test` を通す。E2E を含むタスクでは `npm run e2e` も通す。
3. タスク完了時に、満たした受け入れ基準の ID（例: `AC-HAB-03`）を報告する。
4. **仕様にない機能、画面、ライブラリは追加しない。** 必要だと判断した場合は実装せず、`docs/questions.md` に追記する。
5. 仕様が曖昧で、§15「未解決の論点」に該当する箇所は推測で埋めない。`// TODO(spec): <論点番号> <内容>` を残し、`docs/questions.md` に書いて報告する。それ以外の曖昧さは、この文書の原則（§2）に最も沿う解釈で実装し、`docs/questions.md` に「決めたこと」として1行残す。

### 0.4 記号

- 【盤】【着】【刻】【仕】は由来する元設計書を示す（盤＝生活の盤面、着＝着手支援、刻＝努力管理、仕＝努力の仕組み化）。【統】はこの統合で新たに決めたもの。
- 【自動】は `npm run test` または `npm run e2e` で検証する受け入れ基準。【手動】は人が実機で確認する受け入れ基準。

## 1. 概要

### 1.1 何を解決するアプリか

4つの設計書は、同じ人の別々の悩みに対する4つの道具だった。統合すると、時間の幅が違う3つの層になる。

| 層 | 頻度 | 悩み | モジュール | 由来 |
|---|---|---|---|---|
| 日次 | 毎日 | 続けたいことが続かない／やめたいことがやめられない | **習慣** | 【仕】 |
| 日次 | 毎日 | 初日と詰まった瞬間に逃げる | **着手**（10分ラフタイマー） | 【着】 |
| 都度 | 選択の直前 | 先が読めないまま大事な選択をする | **盤面**（手番と読みシート） | 【盤】 |
| 期間 | 期限ごと | 期限のない努力が足踏みし、自己評価が実測とずれる | **段**（期限・判定・刻み・較正） | 【刻】 |
| 週次 | 週1回 | どれが効いているか分からない | **週次ふりかえり**（感想戦＋週次チェック＋傾向） | 【盤】【仕】【着】 |
| 検証 | 実験期間 | このアプリ自体が効いているか分からない | **実験ランナー**（反証条件つき） | 【盤】【着】【刻】 |

### 1.2 アプリ名

**一手（いって）**。4つの設計書に共通する中心概念が「次の一手」（着手の次の一手メモ、盤面の手番、刻の一段、習慣の1回）であることから名付けた。識別子は `itte`。アプリ名は `src/config.ts` の定数1か所で変えられるようにする。

### 1.3 1日・1週間の使われ方（目標体験）

| タイミング | 行動 | 操作量の上限 | 由来 |
|---|---|---|---|
| 朝 | アプリを開く。「きょうの道」の先頭に光る1つを見る | 0タップ・5秒 | 【盤】【着】 |
| 習慣の時刻 | 習慣カードの「やった」を押す | **1タップ**・3秒 | 【仕】 |
| 手をつけたいとき | やることカードの「始める」を押す → 10分タイマー | **1タップ** | 【着】 |
| 詰まったとき | 「詰まった」→ 何が分からないか1行 → 3択 | 15秒 | 【着】 |
| 逃げたあと | ＋ →「逃げた」→ 選択式3問（全部とばしてよい） | 10秒 | 【着】 |
| 大事な選択の直前 | ＋ →「手番」→ 読みシート | 最短30秒・通常3分 | 【盤】 |
| 選んだあと | 「決めかけの手」ノードで1つ選ぶ | 1タップ＋確定 | 【盤】 |
| 段の期限が来た日 | 判定ノード → 決めておいたことを見る → 実測を入れる | 60秒 | 【刻】 |
| 夜 | 「1日のしめ」3問 | 20秒 | 【着】 |
| 金〜日曜 | 週次ふりかえり（1枚ずつ進むレッスン形式） | 15分以内・途中でやめてよい | 【盤】【仕】 |
| 月初 | 評価関数を見直す（週次ふりかえりの最後に出る） | 2分 | 【盤】 |

### 1.4 作らないもの

この一覧は §2.3 の絶対制約と同じ効力を持つ。

- ログイン、複数ユーザー、サーバー、同期、クラウド保存【着】【仕】【刻】
- 他人との共有・比較・ランキング・フレンド・グループ【刻】【仕】
- ストリーク（連続日数）、XP、ポイント、スコア、バッジ、レベル、リーグ、ハート、ジェム、ショップ、紙吹雪・祝福アニメーション【着】【刻】【仕】【統】
- Web Push 通知、催促、再通知、アプリアイコンのバッジ件数【着】【仕】【統】
- サイトブロック機能【着】
- AI/LLM による提案・励まし・チャット、助言メモ機能【着】【刻】【仕】
- アクセス解析、外部フォント、CDN、その他すべての外部通信【着】【仕】
- Google Calendar API 連携（代わりに `.ics` ファイルの読み込みと書き出しを作る）【統】

## 2. 設計原則

### 2.1 統合原則

4文書の原則を統合し、重複をまとめた。実装判断に迷ったら、上から順に照らす。

| # | 原則 | 実装上の帰結 | 由来 |
|---|---|---|---|
| U1 | **アプリ自体が新しい評価対象にならない** | ストリーク・スコア・褒め言葉を出さない。途切れたときに「失敗した」と感じる仕掛けを置かない | 【着】【仕】【刻】 |
| U2 | **アプリの操作を努力にしない** | 毎日の操作は1タップ。1回の入力は30秒以内。確認ダイアログを出さず、取り消しで対応する | 【仕】【盤】 |
| U3 | **次にやることは常に1つだけ光らせる** | ホームは「きょうの道」。最初の未完了ノードだけを大きく表示する。今日のやることは1件だけ表示する | 【統】【着】 |
| U4 | **最初に作るのは「雑な版」。やめても成功** | 10分で終われば成功扱い。詰まったら1行書けば成功扱い | 【着】 |
| U5 | **失敗はデータとして扱う** | 未記録は「記録なし」と書く。理由は事実を尋ねる形で聞く | 【仕】【着】 |
| U6 | **結果は書き換えられない。結果に応じた行動は結果を見る前に決める** | 判定・実測・予想・事前コミットは追記のみ。訂正は訂正レコードの追記で表す | 【刻】 |
| U7 | **期限のない段は存在できない。登れない段は刻める** | 段の期限は必須。届かなかった段の下に子の段を作る操作を一級機能にする | 【刻】 |
| U8 | **比較対象は過去の自分だけ** | 他者の値を表示する画面を作らない | 【刻】 |
| U9 | **全部を読まない。トリガーに当たった選択だけ読む** | 手番トリガーは有効なもの最大5個 | 【盤】 |
| U10 | **中盤の停滞は見せ方で支える** | 主表示は累積量と週単位の推移。日次の上下は強調しない | 【仕】 |
| U11 | **やめるのも正当な選択肢** | 継続・縮小・終了のボタンを同じ見た目で並べる | 【仕】 |
| U12 | **アプリ自体を仮説検証の道具にする** | 反証条件を最初から組み込み、実験ランナーで判定を表示する | 【盤】【着】【刻】 |
| U13 | **データは端末の外に出ない** | 外部通信ゼロ。エクスポートと全削除は本人の操作でのみ行う | 【着】【仕】【刻】 |

### 2.2 結果非依存フィードバックの原則【統】

Duolingo の手応え（音・振動・アニメーション）を移植するにあたり、U1 と両立させるための追加原則。

> **フィードバック（色・音・振動・アニメーション・文言の調子）は「記録できた」という事実にだけ反応し、記録の中身（やった／記録なし、届いた／届かなかった、好手／悪手）によって変えない。**

例: 判定で「届いた」と「届かなかった」は、同じ色・同じ音・同じアニメーションで「判定を記録しました」と表示する。習慣の「やった」と「記録なし（理由タグ）」も同じ音と同じ「記録しました」を出す。

この原則は §12 の `AC-UX-04` でテストする。

### 2.3 絶対制約（実装の都合で緩めない）

1. UI に表示しないもの: ストリーク（連続日数）、達成率のゲージ、スコア、XP、バッジ、レベル、ランキング、紙吹雪などの祝福演出。【着】【刻】【仕】
2. UI 文言に使わない語: 「すごい」「えらい」「頑張」「失敗」「サボ」「達成」「目標」。感嘆符（`!` `！`）と絵文字も使わない。テストで検査する。【着】【仕】
3. `src/` 内に `streak` `xp` `badge` `confetti` `league` `leaderboard` という識別子を置かない（大文字小文字を区別しない）。テストで検査する。【着】【統】
4. 外部への通信を一切しない。解析ツール、外部フォント、CDN、外部 API を入れない。【着】【仕】
5. 催促する通知、再通知、サイトブロック機能を実装しない。【着】
6. 段（Goal）は期限なしで作れない。UI・リポジトリ関数・シード・インポートのどの経路でも作れない。【刻】
7. 追記専用テーブル（§7.4）のレコードは更新も削除もできない。DB フックで止め、改ざんはハッシュ連鎖で検出する。【刻】【統】
8. 1つの段に判定は最大1件。【刻】
9. 事前コミットは、その段の判定より前にしか作れない。予想は、その段の期限が過ぎる前（＝判定の実測より前）にしか作れない。【刻】
10. 有効な手番トリガーは最大5件。有効な評価関数は同時に最大1件（期間が重ならない）。【盤】
11. フィードバックは結果非依存（§2.2）。【統】

### 3.2 仕様レベル

| # | 論点 | 元の記述 | 採用 | 理由 |
|---|---|---|---|---|
| D12 | 日付の境界 | 【着】午前4時。【仕】0時（ローカル日付）。【盤】Asia/Tokyo の0時、週は月曜0時 | **全モジュールで午前4時を境界とする「論理日」**を使う。週は ISO 週（月曜始まり）を論理日で数え、境界は月曜4:00 | 深夜1時の習慣や作業を前日に含めたい、という【着】の理由はほかのモジュールにも当てはまる。境界が2種類あると「今日」の定義がずれて集計が壊れる |
| D13 | タイムゾーン | 【盤】Asia/Tokyo 固定。【着】【仕】端末ローカル | **端末ローカル**。テストは `TZ=Asia/Tokyo` で実行 | 端末内アプリなので端末の時刻が正。利用者は日本在住 |
| D14 | 週の数え方 | 【盤】【仕】ISO 週。【着】実験開始日からの7日区切り | 週次ふりかえり・週次チェック・感想戦は **ISO 週**。実験のフェーズだけ **実験開始日からの7日区切り** | 目的が違う。カレンダー上の振り返りと、実験の条件切り替えは別物 |
| D15 | 実験デザインの重複 | 【盤】ベースライン2週→8週。【着】1週ごとの ABAB を4週。【刻】A2週・B4週・A2週・B4週 | **実験ランナー**（§9）に統合。プリセット3種から**同時に1つだけ**実行できる。実行中でないモジュールは常にフル機能（B条件） | 3つの ABAB を同時に回すと、条件の切り替えが互いに交絡して、どの仮説も判定できなくなる |
| D16 | ホーム画面 | 【盤】ホーム＝盤面ボード。【着】ホーム＝今日のタスク1件。【仕】ホーム＝今日の習慣カード一覧 | **ホーム＝「きょうの道」**（§6.3）。習慣、今日のやること1件、判定待ち、決めかけの手、1日のしめ、週次ふりかえりを1本の道に並べる。盤面は独立タブにし、ホームには評価関数と直近の期限だけを細い帯で出す | Duolingo の「道」と【着】の「今日は1件だけ見せる」を同時に満たす |
| D17 | 盤面の期限と段の期限 | 【盤】BoardItem の締切。【刻】Goal の期限（ダッシュボードに7日以内を表示） | 盤面タブで **BoardItem と Goal の期限を1つのリストに合成**して表示する。データは重複させない | 同じ「期限」を2か所で管理すると、片方だけ更新されてずれる |
| D18 | 盤面の締切とやること | 【盤】締切・案件。【着】Task（予定日つき） | Task に `boardItemId`（任意）を持たせる。盤面の項目から「10分だけ手をつける」で、紐づいたやることを作れる | 盤面で見えた締切から、そのまま着手につなげるため |
| D19 | 評価関数と段 | 【盤】期間ごとに最優先指標1つ。【刻】指標と閾値と期限を持つ段 | 別エンティティのまま残す。評価関数は「候補手を比べる物差し」、段は「判定される約束」 | 役割が違う。評価関数は数値でなくてよい（【盤】）が、段の指標は数値必須（【刻】） |
| D20 | 週次の振り返りが3つある | 【盤】感想戦。【仕】週次チェック。【着】週次レポート | **1本の「週次ふりかえり」レッスン**（§6.9）にまとめる。数字 → 感想戦 → 習慣チェック → 傾向と対策 → 足踏み → しめ、の順で1枚ずつ進む | 週に3回も振り返り画面を開かせると U2 に反する |
| D21 | 週次の振り返りを出す曜日 | 【盤】日曜夜。【仕】金〜日曜 | **金曜4:00〜翌週火曜4:00**に、その週のふりかえりノードを出す | 金曜から出せば日曜に忙しくてもできる。月曜にやり残した場合のために翌火曜まで延長する |
| D22 | 未記録の表記と禁止語 | 【刻】「達成／未達」「目標」。【仕】「達成率」。【着】これらを禁止語に指定 | UI では **段**（目標の代わり）、**届いた／届かなかった**（達成／未達の代わり）、「28日間で 4/6 回」（達成率の代わり）を使う。識別子（`MET`/`UNMET` など）は英語のまま | 禁止語は UI 全体に適用する（§2.3-2） |
| D23 | 悪手という語 | 【盤】好手／普通／悪手 | 残す | 禁止語に含まれず、将棋の比喩の中核。判断の質を記録する語であり、本人の人格評価ではない |
| D24 | 感嘆符・絵文字 | 【仕】使わない | 全画面で使わない（§2.3-2） | 【仕】の文言方針を全モジュールに広げる |
| D25 | ルーター | 【着】HashRouter。【仕】BrowserRouter＋404.html のリダイレクト | **HashRouter**（`createHashRouter`） | 静的ホスティングで確実に動き、オフラインでも壊れない。PWA の単体起動では URL がほとんど見えないため、ハッシュの見た目の欠点は小さい |
| D26 | CSS | 【着】CSS Modules、CSS フレームワークなし。【盤】【仕】Tailwind | **Tailwind CSS v4**＋CSS 変数のデザイントークン（§5） | 2対1。デザイントークンを一元管理しやすい。UI コンポーネントライブラリは使わない（【着】の意図は守る） |
| D27 | ID と時刻の型 | 【盤】uuid。【刻】cuid／DateTime。【着】randomUUID／epoch ms。【仕】randomUUID／ISO 文字列 | ID は `crypto.randomUUID()`。瞬間は **epoch ms（number）**、日付は **LocalDate（`YYYY-MM-DD`）**。エクスポート時だけ ISO 文字列に変換 | 比較と並べ替えが速く、タイムゾーンの変換ミスが起きない |
| D28 | Service Worker の更新方式 | 【着】【仕】`autoUpdate`（自動で再読み込み） | **`prompt`** にし、ホームとタブ画面でだけ「新しい版があります［更新］」のスナックバーを出す。レッスン・タイマー・ウィザード中は出さない | 自動再読み込みは、ウィザードの入力途中を消す。Duolingo もレッスン中は割り込まない |
| D29 | 今日のやることの持ち越し | 【着】`plannedFor` が今日のものだけを表示（過去日のものは消える） | 過去日の未完了は「持ち越し」カードで「今日に移す／片づける」を選ばせる。移すと `plannedFor` を今日に変え、元の日付を `planHistory` に残す | 消えたままだと着手の機会を失う。一方で元の予定日を上書きすると着手率の分母が変わるので、履歴として残す（§9.3） |
| D30 | やることの完了 | 【着】`archivedAt` はあるが、片づける操作が未定義 | やることのメニューに「片づける」を置き、`archivedAt` と `closedReason`（`done`／`dropped`）を入れる | 定義漏れの補完 |
| D31 | 盤面のベースライン期間の記録方法 | 【盤】最初の2週は読みシートを使わず感想戦だけ。ただし手の記録方法が未定義 | 読みシートを使わない手の記録として**簡易記録**（局面1行＋選んだこと1行）を作る。`Move.mode = 'quick'` | 感想戦の対象となる手がなければ、ベースラインの悪手率を測れない |
| D32 | 「事後の気づき」指標のデータ | 【盤】「トリガー外で後から読むべきだったと記録した手」を数えるが、該当フィールドがない | `Move.retro: boolean`（あとから記録）を追加 | 指標を計算できるようにするための補完 |
| D33 | 判定要求の時刻 | 【刻】日次バッチが検出した時刻を `requestedAt` にする。クライアントの初回取得時刻は使わない | `requestedAt` ＝ **期限日が終わる瞬間**（期限日の翌日の4:00）。アプリが初めて検出した時刻は別に `detectedAt` に残す | サーバーのバッチがない。アプリを開かなかった日数も回避の一部なので、開いた時刻ではなく期限を起点にするのが【刻】の意図に沿う |
| D34 | 期限の延長が許される時期 | 【刻】延長には理由が必須（時期は未定義） | 延長は**期限日まで**（論理日で `today <= deadline`）。期限を過ぎたら判定を先にする | 判定待ちになってから延長できると、判定を避ける経路になる |
| D35 | 未達のあとの3択 | 【刻】図では「刻む／切り直す／取り下げる」。スキーマには `WITHDRAWN` があるが経路が未定義 | 3択の結果を追記専用の `GoalFollowUp` に記録する。段の状態は `UNMET` のまま変えない。`WITHDRAWN` は使わないので enum から削除 | 【刻】の受け入れ条件「未達の段から子を作っても親は UNMET のまま」と整合させるため |
| D36 | 感情予想の取り方 | 【刻】着手前の苦痛の強さと持続時間。予想を先に記録しないと測定画面に進めない。ただし頻度は低く保つ | 段に紐づいたやることの10分タイマーを始めるとき、**その段につき1日1回まで**、開始前に予想シート（強さ0〜10、持続）を出す。「とばして始める」も同じ大きさで並べる。実際の値はセッション終了画面で聞く | 【着】の「1タップで開始」と衝突するので、頻度を絞り、とばせるようにした |
| D37 | 較正誤差の単位 | 【刻】`E = mean(p - a)`。単位の違う指標をそのまま平均している。符号の向きも指標の方向を考えていない | 指標の方向で符号をそろえ（正＝予想が実測より良い側）、段の閾値で割って正規化した値の平均を主指標にする。指標ごとの生の差も表示する | 「分」と「点」を足すと意味がなくなるため。符号の意味（正＝過大評価）は【刻】の意図どおり |
| D38 | 理由のタグが3種類ある | 【仕】習慣の未記録理由タグ。【着】逃避前の状態。【盤】見落としタグ | 統合しない。3種類とも残す | それぞれ別の仮説を検証するためのデータで、混ぜると全部判定できなくなる |
| D39 | エクスポート形式 | 【着】CSV を6ファイル別々に。【仕】JSON（インポート可）。【刻】判定・予想・延長の CSV | **JSON 完全バックアップ**（インポート可）＋**CSV 一式を1つの zip** | 複数ファイルの連続ダウンロードはブラウザにブロックされやすい |
| D40 | 確認ダイアログ | 【仕】日々の操作に確認ダイアログを出さない。【着】全削除は2段階確認 | 日々の操作は取り消し（スナックバー）。**取り消せない操作**（判定の確定、全削除、インポート）だけ確認を挟む。判定は Duolingo の「確かめる → 確定」の2段ボタンで行う | 取り消せない操作に取り消しボタンは出せないため |
| D41 | 期限の「未来日付」 | 【刻】期限は未来日付 | `deadline > today`（論理日）。今日を期限にはできない | 定義の明確化 |
| D42 | 盤面の資源 | 【盤】お金・空き時間を表示 | `BoardItem.type = 'resource'` の項目として、タイトルに自由記述（例: 今月の残り 2万円）。数値計算はしない | MVP の範囲を越えないため |
| D43 | `navigator.storage.persist()` | 【仕】起動時に要求 | 起動時に要求し、設定画面に状態を表示する | 変更なし |
| D44 | 外部フォント | 【着】【仕】使わない | システムフォントのうち丸ゴシックを優先する（§5.3） | Duolingo の柔らかい印象を外部通信なしで近づけるため |

## 4. UX 戦略

### 4.1 Duolingo のどこが効いているのかを分解する

Duolingo の UX は、2種類の仕組みが重なってできている。

- **摩擦を消す仕組み**: 次にやることが常に1つ光っている「道」。1画面1問のレッスン。画面下の大きなボタン。押した瞬間の音・振動・色。登録なしで始められるオンボーディング。数分で終わる区切り。
- **評価と報酬の仕組み**: ストリーク、XP、リーグ、ハート、ジェム、祝福アニメーション、「Duo が悲しんでいます」通知。

このアプリでは前者だけを移植する。後者は、3つの元設計書が「評価の対象が増えると着手時の脅威が増し、回避が強まる」「測定値を歪める」という仮説に基づいて禁止しているため、移植しない（D1）。

### 4.2 移植・変換・不採用の対応表

| Duolingo の要素 | 扱い | このアプリでの形 |
|---|---|---|
| 道（パス）と光る次の1つ | **移植** | ホーム「きょうの道」。最初の未完了ノードだけを大きく展開し、主ボタンを持たせる（§6.3） |
| 1画面1問のレッスン | **移植** | 習慣作成・ラフ登録・読みシート・段の登録・判定・週次ふりかえりをすべて `LessonShell`（§5.8）で作る |
| 上部のレッスン進捗バー | **移植** | レッスン内のステップ表示（例: 2/4）。**アプリ全体や1日の進み具合を示すゲージは作らない**（§2.3-1） |
| 画面下の大きな主ボタン | **移植** | 全レッスンで画面下固定。高さ56px、押すと沈む立体ボタン |
| 「確かめる → 続ける」の2段ボタン | **移植** | 取り消せない操作（判定の確定）に限って使う |
| 押した瞬間の音・振動・色 | **移植（結果非依存）** | 記録した事実にだけ反応する。内容によって変えない（§2.2） |
| 不正解のときの赤いシート | **不採用** | 赤は破壊的操作（削除）にしか使わない。入力の不備は文で伝える |
| レッスン完了画面 | **変換** | セッション終了画面・週次ふりかえり完了画面に、**事実の要約**（時間・件数・次の一手）だけを出す。褒め言葉は出さない |
| 登録なしで始めるオンボーディング | **移植** | タイプ診断5問を1問ずつ自動送りで出し、そのまま最初の1件を作る。最初の記録まで90秒以内（§6.4） |
| マスコット（Duo） | **変換** | 案内役「コマ」（将棋の駒の形）。案内と空の状態にだけ出し、**結果に反応して表情を変えない**（§5.7） |
| ストリーク | **不採用 → 代替** | 習慣ごとの**累積量**（「これまで合計 55分」）と**週ごとの棒グラフ**（U10） |
| ストリークフリーズ・修復 | **不採用 → 代替** | 「記録なし」のまま理由タグを1タップで残せる。途切れという概念自体を持たない |
| XP・デイリークエスト | **不採用** | ― |
| ハート（ミスで減る） | **不採用 → 反転** | 詰まりボタン。詰まることを記録の対象にして、詰まっても成功扱いにする（U4） |
| リーグ・フレンド | **不採用** | 比較対象は過去の自分だけ。較正画面（§6.8.7）が「過去の自分との比較」を担う |
| 祝福アニメーション | **不採用 → 代替** | 300ms の中立なチェックの描画アニメーション1種類だけ。結果によって変えない |
| 催促通知 | **不採用 → 代替** | `.ics` 書き出しで、本人が自分のカレンダーに予定を入れる（D8） |
| ホーム画面ウィジェット | 不採用 | PWA では作れない |
| 練習・まちがえた問題の復習 | **変換** | 週次ふりかえりの感想戦（悪手の見直し） |
| 新機能の段階的な解放 | **変換** | 機能を「報酬として解放」はしない。すべての機能は最初から ＋ と記録庫から使える。ホームの道には、データがあるモジュールのノードだけが並ぶ（結果として段階的に見える） |
| ガイドブック（ユニットの解説） | **移植** | 各レッスンの初回だけ「はじめての○○」カードを1枚出す（`introSeen` に記録） |

### 4.4 操作量の予算

アプリを開いてからの操作量。`AC-UX-01`〜`03` で E2E テストする（タップ数は Playwright で数える）。

| 操作 | タップ数の上限 | 時間の目安 | 由来 |
|---|---|---|---|
| 習慣を「やった」と記録する | **1** | 3秒 | 【仕】 |
| 今日のやることの10分タイマーを始める | **1**（感情予想シートが出る日は2） | 3秒 | 【着】 |
| 記録なしの日の理由を残す | **1**（タグ1つ） | 5秒 | 【仕】 |
| 決めかけの手を確定する | **2**（候補を選ぶ → 確定） | 5秒 | 【盤】 |
| 逃避ログ | **3**（＋ → 逃げた → 保存）。全項目とばしてよい | 10秒 | 【着】 |
| 1日のしめ | 4 | 20秒 | 【着】 |
| ラフ登録 | 3項目の入力＋1 | 45秒 | 【着】 |
| 読みシート（必須項目のみ） | 局面と候補2つの入力＋3 | 30秒 | 【盤】 |
| 判定 | 実測1つと記述1つの入力＋2 | 60秒 | 【刻】 |
| 週次ふりかえり | ― | 15分以内。どこでやめても入力済みの分は保存される | 【盤】【仕】 |

### 4.5 文言の方針

- 事実を短く書く。完了は「記録しました」「判定を記録しました」程度にとどめる。【仕】
- 記録がない日は「記録なし」と書く。「できなかった」とは書かない。【仕】
- 理由は「何があった?」と事実を尋ねる。【仕】
- ボタンは動詞の辞書形（「始める」「記録する」「つぎへ」）。見出しは名詞か短い問い。
- 文体はやわらかい常体寄り（「何があった?」「あとで決める」）。です・ます調は、説明文と注意書きにだけ使う。
- 禁止語・感嘆符・絵文字を使わない（§2.3-2）。
- UI 文言はすべて `src/copy/ja.ts` に集約する。コンポーネントに直接書かない。主要な文言は付録 A に確定版を載せる。

## 5. デザインシステム

### 5.1 方向性

「明るく、柔らかく、押したくなる」。Duolingo から引き継ぐのは、太い角丸、押すと沈む立体ボタン、大きな文字、余白の多さ、1画面1つの焦点。引き継がないのは、成功の緑と失敗の赤という対比である。このアプリでは**結果を色で表さない**（§2.2）。

### 5.2 色トークン

`src/styles/tokens.css` に CSS 変数で定義し、Tailwind v4 の `@theme` から参照する。ダークモードは `prefers-color-scheme` に追従する（手動切り替えなし【仕】）。

| トークン | ライト | ダーク | 用途 |
|---|---|---|---|
| `--bg` | `#F7F7F4` | `#111418` | 画面背景 |
| `--surface` | `#FFFFFF` | `#1A1E24` | カード |
| `--surface-2` | `#F0F0EB` | `#232831` | 押せない面、入力欄の背景 |
| `--border` | `#E2E2DC` | `#2F353E` | 枠線、カードの下辺 |
| `--text` | `#1F2328` | `#E8EAED` | 本文 |
| `--text-2` | `#5B616B` | `#A3AAB4` | 補足 |
| `--primary` | `#2563EB` | `#4C8DFF` | 主ボタン、光るノード、記録済みの印 |

### 5.4 形・余白・立体

- 余白は 4px 単位。画面の左右は 16px。カードの内側は 16px。カード同士の間は 12px。
- 角丸: カード 16px、ボタン 16px、チップ 999px（丸）、ボトムシート上端 24px。
- **立体ボタン**: `border-bottom: 4px solid var(--primary-edge)`。押している間は `transform: translateY(2px)` と `border-bottom-width: 2px`。無効状態は `--surface-2` の面に `--border` の下辺、文字は `--text-2`。
- カードは影を使わず、`1px solid var(--border)` と `border-bottom-width: 3px` で浮かせる。
- 画面下固定のボタン領域は `padding-bottom: max(16px, env(safe-area-inset-bottom))`。

### 5.5 動き

| 動き | 時間 | 曲線 | 用途 |
|---|---|---|---|
| 押下 | 80ms | `ease-out` | ボタンが沈む |
| シート | 220ms | `cubic-bezier(.2,.8,.2,1)` | ボトムシート、フィードバックシートの出入り |
| 展開 | 200ms | 同上 | 道のノードの展開・折りたたみ |
| チェックの描画 | 280ms | `ease-out` | 記録した瞬間のチェックアイコン（SVG の stroke-dashoffset） |
| 画面遷移 | 200ms | 同上 | View Transitions API が使える環境だけ。横スライド |

- `prefers-reduced-motion: reduce` のときは、すべて不透明度の変化（120ms）だけにする。
- 演出のためだけの動き（跳ねる、回る、紙吹雪、数字が増えていくカウントアップ）は作らない。

### 5.6 音と振動

外部音源は使わず、Web Audio API で合成する（`src/ui/feedback/sound.ts`）。設定で個別に切れる。既定はどちらもオン。

| イベント ID | 音 | 振動（`navigator.vibrate`） | 使う場面 |
|---|---|---|---|
| `recorded` | 523Hz→784Hz の2音、各60ms、音量0.08、正弦波 | `8` | 何かを記録した瞬間すべて（やった、記録なし、判定、感想戦、逃避ログ…） |
| `timerEnd` | 659→784→988Hz の3音、各120ms、音量0.1 | `[20, 40, 20]` | 10分タイマーが0:00になったとき |
| `sheetOpen` | なし | なし | ― |

- **イベント ID は記録の種類と結果に依存しない。** 判定が「届いた」でも「届かなかった」でも `recorded` を鳴らす（§2.2）。
- iOS Safari は `navigator.vibrate` を持たない。存在しなければ何もしない。
- 音は、最初のユーザー操作で `AudioContext` を `resume()` してから鳴らす。

### 5.7 案内役「コマ」

Duolingo の Duo に当たる案内役。将棋の駒の五角形に、点の目が2つあるだけの簡素な形（オリジナルの意匠）。`src/ui/mascot/Koma.tsx` に SVG で描く。外部画像は使わない。

| ポーズ | 使う場面 |
|---|---|
| `wave` | オンボーディングの最初と最後 |
| `point` | 空の状態（ボタンの方を指す） |
| `read` | 読みシートの初回説明、週次ふりかえりの最初 |
| `sit` | オフライン表示、データがまだ足りない状態（「まだ傾向を出せるだけのデータがありません」） |

**守る規則**:

1. 表情は1種類だけ。結果（やった／記録なし、届いた／届かなかった）に応じて表情やポーズを変えない。
2. 判定画面、タイマー画面、逃避ログ、詰まりシートには出さない（評価されている感覚を生む場所に置かない）。
3. セリフは操作の案内だけ。褒める・励ます・心配するセリフを書かない。
4. 吹き出しの文言も `src/copy/ja.ts` に置き、禁止語テストの対象にする。

### 6.3 きょう（ホーム）

#### 6.3.1 レイアウト（上から）

1. **ヘッダー**: 論理日の日付（例: 10/19(月)）。右に設定へのアイコン。
2. **盤面の帯**（盤面モジュールのデータがあるときだけ）: 1行目に有効な評価関数の指標（例: 「評価関数: 卒業研究の章数」）。2行目に直近の期限のチップを最大3つ（例: 「ゼミ発表 あと2日」）。帯を押すと `#/board`。有効な評価関数がない場合で、盤面モジュールを使ったことがある（Move か BoardItem が1件以上ある）ときは、帯の代わりに `Banner`「評価関数を決める」→ `#/settings/evaluation`【盤】。
3. **割り込みカード**: §6.3.3 の優先順で最大2枚まで。3枚目以降は次の起動か、カードが片づいたあとに出す。
4. **きょうの道**: §6.3.2 のノードを縦に並べる。最初の未完了ノードだけ `next` 状態で展開する。
5. **折りたたみ**: 「今日は予定のない習慣」（初期は閉じる。予定外の日の実行を記録できる【仕】）、「他のやること {n}件」（初期は閉じる【着】）。
6. **小さなリンク**: 「過去の記録を直す」→ 過去3日分の習慣の記録・取り消しができるボトムシート【仕】。

習慣・やること・段・手のどれも1件もないときは、道の代わりに `EmptyState`（コマ `point`、「まずは1つだけ。あとから増やせます」、主ボタン「最初の1つをつくる」→ オンボーディングの入口選択と同じ4択シート）を出す【仕】。

#### 6.3.2 道のノード

並び順は §8.10 `buildTodayPath` が決める。ノードの種類と表示:

| ノード | 条件 | `next` のときの表示 | `todo` のときの表示 | 完了の条件 | 由来 |
|---|---|---|---|---|---|
| 判定 | 期限を過ぎ、判定がない段（実験で判定の強制が切られている期間は出さない） | 段のタイトル、「期限 10/18 を過ぎました」、主ボタン「判定する」 | タイトル＋小ボタン「判定する」 | 判定を記録した | 【刻】 |
| 決めかけの手 | 決定していない Move（作成から7日以内） | 局面、候補手のチップ、主ボタン「決める」 | 局面＋小ボタン「決める」 | 決定した | 【盤】 |
| 習慣 | 今日が予定日の active な習慣 | 行動名、実行意図の1文、主ボタン「やった」（長押しで量の入力） | 行動名＋小ボタン「やった」 | 今日の記録がある（done=true） | 【仕】 |
| やること | 今日のやること（1件だけ） | 次の一手（なければタイトル）、主ボタン「始める」（`--accent`） | 同左の1行＋小ボタン「始める」 | 今日そのやることでセッションを1回以上始めた | 【着】 |
| 週次ふりかえり | 金曜4:00〜翌週火曜4:00 で、その週のふりかえりが未完了 | 「今週のふりかえり（15分）」、主ボタン「始める」 | 1行＋小ボタン | 完了した | 【盤】【仕】 |
| 1日のしめ | 毎日。着手モジュールを使ったことがあるとき（やることかセッションが1件以上） | 「1日のしめ（20秒）」、主ボタン「答える」 | 1行＋小ボタン | 今日の DailyCheck がある | 【着】 |

- **習慣のノードは `todo` 状態でも「やった」ボタンを持つ。** どの習慣も1タップで記録できる（予算 §4.4）。
- 習慣の記録済み表示: 「記録済み {量}{単位}」＋「取り消す」＋「追加で記録」【仕】。
- 習慣ノードには、ペルソナ `optimist` のとき「今週 {done}/{scheduled} 回」を添える【仕】。
- 実験の A 条件（着手プリセット）では、やることのノードに次の一手を出さず、タイトルを出す【着】。
- 完了したノードは `done` 状態（1行、記録済みの印）で道に残す。翌日（論理日）に消える。
- 今日の道に「今日は何割終わった」などの集計は出さない（§2.3-1）。

#### 6.3.3 割り込みカード

| 優先 | カード | 条件 | 中身 | 由来 |
|---|---|---|---|---|
| 1 | 再開 | 進行中のセッション（`endedAt = null` で、開始から10分未満）がある | 「10分タイマーの途中です 残り 6:12」、主ボタン「戻る」 | 【着】 |
| 2 | 記録なしの理由 | `pendingReasonPrompts` が1件以上 | 「10/16(金) 読書 は記録なし。何があった?」＋理由タグのチップ（折り返し）＋「理由なし」＋「あとで」。タグを1つ押した時点で `recordMissed` し、次の1件に進む。カードは1枚のスタックとして数える | 【仕】 |
| 3 | 持ち越し | 予定日が今日より前で、片づけていないやることがある | 「昨日までのやること {n}件」、「今日に移す」「片づける」（1件ずつ） | 【統】D29 |
| 4 | 記録の整合性 | 台帳の検証に失敗した | 「記録の一部が変更されています」→ `#/settings/data` | 【統】D5 |
| 5 | バックアップ | `lastExportAt` が7日以上前、または未設定で記録が1件以上 | 「この端末にだけ保存されています。書き出しておきますか」、「書き出す」「あとで」 | 【仕】 |

「あとで」を押したカードは、その論理日の間は出さない（`sessionStorage` ではなく `Settings.dismissed` にカード ID と論理日で保存）。

#### 6.3.4 起動時の処理

`src/db/init.ts` の `onLaunch(now)` を、アプリ起動時と `visibilitychange` で `visible` になったときに実行する。

1. `navigator.storage.persist()` を要求する（初回のみ）【仕】。
2. 放置セッションの検出（§8.4.3）。該当があれば `abandoned` にして閉じ、逃避ログを促すシートを1回だけ出す【着】。
3. 期限到来の検出（§8.7.3）。判定待ちを確定する【刻】。
4. 足踏みの検出（§8.7.5）【刻】。
5. 今日の `AppOpen` を記録する（実験の使用率の計算用、§9）。
6. アイドル時に台帳の検証を実行する（§7.5）。

### 6.4 オンボーディング（`#/onboarding`）

目標: 起動から最初の記録まで90秒以内。登録・ログインはない。

| ステップ | 画面 | 操作 |
|---|---|---|
| 1 | コマ（`wave`）、アプリ名、1文「次にやる一手だけを、軽く記録するアプリです」、補足「データはこの端末の中だけに保存されます」 | 主ボタン「はじめる」 |
| 2〜6 | タイプ診断の5文を1文ずつ。`ScaleInput`（5段階、`autoAdvance`）。右上に「スキップ」 | 選ぶと250ms後に自動で次へ【仕】 |
| 7 | 「いま、いちばん近いのは?」4つの大きな選択カード | 1つ選ぶと、そのレッスンへ直接遷移 |

タイプ診断の5文【仕】:

| persona | 文 |
|---|---|
| `regret` | やるべきことはわかっているのに、できずに後悔することが多い |
| `optimist` | 努力しなくても、たいていは何とかなると思う |
| `meaning` | 続けている途中で「これに意味があるのか」と止まってしまう |
| `selfblame` | 続かないのは自分の意志が弱いからだと思う |
| `notfun` | 努力はそもそも楽しくない |

最も高いスコアの persona を設定する（同点なら表の上にあるもの）【仕】。スキップした場合は `persona = null`。

ステップ7の選択肢:

| カード | 遷移先 |
|---|---|
| 続けたいこと、やめたいことがある | `#/habits/new` |
| 手をつけられていないことがある | `#/tasks/new?start=1` |
| 迷っている選択がある | `#/moves/new` |
| 期限を決めて確かめたいことがある | `#/goals/new` |

カードの下に小さく「あとで決める」→ ホーム。どれを選んでも、遷移の時点で `settings.onboarded = true` にする。最初の記録が終わったら、割り込みカード6「ホーム画面に追加」を出す。

### 6.5 習慣モジュール【仕】

#### 6.5.1 習慣作成（`#/habits/new`、4ステップのレッスン）

| ステップ | 問い | 入力 | 検証 |
|---|---|---|---|
| 1 種類 | 「始めたい? やめたい?」 | 2つの大きなカード「始めたい」「やめたい」。「やめたい」なら `replacesText`「やめたいこと」を入力し、見出しが「代わりに何をする?」に変わって次の行動名の入力に導く | `kind=replace` なら `replacesText` 1〜40文字 |
| 2 行動と量 | 「何を、どれだけ?」 | 行動名、目的（任意。`meaning` では必須）、単位（チップ: 回・分・ページ・その他）、1回の量、「絶対にできる量」。`smallStartSuggestion` が値を返したら、量の下に「最初は {n}{単位} から始めてみませんか」と「そうする」チップ | 行動名 1〜40、目的 0〜200、単位 1〜10、量は正の整数、絶対にできる量は 1 以上 量以下 |
| 3 いつ・どこで | 「いつ、どこでやる?」 | 曜日（7つのトグル。チップ「毎日」「平日」「土日」で一括）、時刻またはきっかけ行動（どちらか必須）、場所、やり方（任意）、環境設計メモ（任意。`regret` では必須）。`notfun` なら「楽しくする工夫」欄を追加 | 曜日1つ以上、`time` か `cue` の少なくとも一方、場所 1〜40、やり方 0〜80 |
| 4 確認 | 「この形で始める」 | `formatIntention` の1文を `display` サイズで表示。主ボタン「この内容で始める」 | ― |

保存後は `FeedbackSheet`「記録しました」を出してホームに戻る。

#### 6.5.2 ペルソナ別の差分【仕】

| persona | 変更点 |
|---|---|
| `regret` | 作成ステップ3で環境設計メモ（`commitmentNote`）を必須にする |
| `optimist` | ホームの習慣ノードに「今週 {done}/{scheduled} 回」を添える |
| `meaning` | 目的（`purpose`）を必須にする。習慣のレビュー間隔を14日にする（既定28日） |
| `selfblame` | 小さく始めるガードの倍率を 1.5 にする（既定2） |
| `notfun` | 作成ステップ3に「楽しくする工夫」（`funNote`）欄を出し、詳細画面に表示する |

#### 6.5.3 習慣の詳細（`#/habits/:id`）

上から:

1. 実行意図の1文（`h2`）、目的
2. **累積量**を大きく（`display`）:「これまで合計 55分」【仕】U10
3. 直近28日:「28日間で 4/6 回」（分子と分母を必ず併記。割合のゲージは出さない）
4. 週ごとのグラフ: `WeeklyBarChart`（12週、実行回数の棒＋予定回数の目安線）
5. 月間カレンダー: `MonthCalendar`
6. 量を上げる提案: `levelUpSuggestion` が値を返したら「量を {n}{単位} に上げてみませんか」＋「上げる」「今はしない」
7. 自動化スコアの推移（折れ線、週次チェックの平均）
8. 記録なしの理由の内訳（`reasonBreakdown`、件数の降順）
9. 登録した対策（Countermeasure の一覧）
10. 定着の提案: `graduationEligible` が true なら「定着したようです」＋「定着済みにする」
11. 「楽しくする工夫」（`notfun` のとき）
12. ボタン: 「編集」、状態の変更（「定着済みにする」「終了する」「再開する」）、「カレンダーに書き出す」（`time` があるときだけ。`.ics`）

連続日数は表示しない（D2）。

#### 6.5.4 習慣の編集（`#/habits/:id/edit`）

作成ウィザードと同じ項目を1ページのフォームで表示し、既存値を初期値にする【仕】。量を変えたら `amountChangedOn` を今日にする。

#### 6.5.5 習慣の一覧（`#/library/habits`）

「実行中」「定着済み」「終了」の3セクション。各行に行動名と「28日間で {done}/{scheduled} 回」。右上に「新しい習慣」【仕】。

#### 6.5.6 過去の記録を直す（ボトムシート）

今日と過去3日（論理日）の4日分を日付チップで選び、その日の予定習慣ごとに「やった」「記録なし（理由タグ）」「取り消す」を操作する。4日以上前と未来の日は操作できない【仕】。

### 6.6 着手モジュール【着】

#### 6.6.1 ラフ登録（`#/tasks/new`、3ステップのレッスン）

| ステップ | 問い | 入力 | 検証 |
|---|---|---|---|
| 1 | 「何に手をつける?」 | `title`。盤面の項目から来た場合は、その項目のタイトルを初期値にする | 1〜80文字、必須 |
| 2 | 「10分で作れる、出来の悪い版は?」 | `roughVersion`。補足「完成形は書かない。見出しだけ、箇条書き3つだけ、など」 | 1〜80文字、必須 |
| 3 | 「最初の物理的な動作は?」 | `firstAction`。補足「例: エディタを開いて見出しを3つ書く」。段との紐づけ（任意、段のチップ）。予定日 `plannedFor`（既定は今日、チップ「今日」「明日」と日付入力） | 1〜80文字、必須 |

- 主ボタンは「保存」と「保存して始める」の2つ（後者が主、`--accent`）。`?start=1` で来た場合は「保存して始める」だけを出す。
- **実験の A 条件（着手プリセット）**: ステップ2と3を出さず、ステップ1だけにする。`roughVersion` と `firstAction` は null で保存し、必須を外す【着】。

#### 6.6.2 やることの詳細（`#/tasks/:id`）

タイトル、雑な版、最初の動作、次の一手、予定日、紐づいた段・盤面の項目、セッションの履歴（日時・長さ・終わり方）、詰まりの履歴。ボタン: 「始める」、「編集」、「片づける」（`done`／`dropped` をチップで選ぶ。D30）。

#### 6.6.3 感情予想シート（開始前、条件付き）【刻】D36

やることが段に紐づいていて、その段の感情予想が今日（論理日）まだなく、実験で着手プリセットの A 条件中でないとき、「始める」を押すと開始前にボトムシートを出す。

- 「どれくらいしんどそう?」0〜10 のチップ（0 と 10 にラベル「平気」「とてもしんどい」）
- 「そのしんどさは何分くらい続きそう?」チップ: 1分・5分・10分・30分・それ以上（60）
- ボタン: 「記録して始める」（主）と「とばして始める」（同じ大きさの secondary）

どちらのボタンでもセッションは即座に始まる。

#### 6.6.4 10分タイマー（`#/session/:id`）

- 全画面。下部タブなし。`RingTimer` に残り時間（mm:ss）。
- 残り時間は state に持たず、`Session.startedAt` から毎秒計算する。リロードしても、ブラウザを閉じても正しく復元される【着】。
- リングの下に `firstAction`（A 条件では `title`）を大きく表示する。
- ボタン: 「詰まった」（secondary、A 条件では出さない）、「中断」（ghost）。
- Screen Wake Lock API で画面の消灯を防ぐ（対応環境のみ。終了時と画面離脱時に解放）【統】。
- `document.title` を「6:12 一手」の形で毎秒更新する。
- 0:00 になったら `timerEnd` の音と振動を出し、`#/session/:id/end` に遷移する。バックグラウンド中に 0:00 を過ぎた場合は、前面に戻った時点で遷移する。

#### 6.6.5 詰まりシート（タイマー上のモーダル）

- 「何が分からない?」1行（`blocker`、1〜80文字、必須）。
- 3つの選択ボタン（同じ見た目）: 「雑に埋めて進む」（`fill`）／「5分だけ調べる」（`research5`）／「次の一手を書いて止める」（`stop`）。
- `fill` と `research5`: StuckLog を保存してタイマーに戻る。**タイマーは止めない**【着】。
- `stop`: StuckLog を保存し、Session を `stopped` で閉じて終了画面へ。
- 保存時の文言は「記録しました。タイマーは続いています」（`FeedbackSheet`。`stop` の場合は「記録しました」）。励ましの言葉は足さない。

#### 6.6.6 セッション終了（`#/session/:id/end`）

- 事実の要約: 「{n}分 取り組みました」。
- 感情予想を記録していた場合: 「実際のしんどさは?」0〜10 と「何分くらい続いた?」（§6.6.3 と同じチップ）。任意。
- 「続ける」と「やめる」を同じ大きさで並べる（U11）。
- 「やめる」を選ぶと「次の一手」入力欄を出す（1〜80文字、B 条件では必須）。補足「次に開いたとき、これだけが表示されます」。
- 「続ける」: 前のセッションを `continued` にし、同じやることの新しいセッションを作ってタイマーへ。
- 「やめる」: `stopped`、`Task.nextStep` を更新してホームへ。
- A 条件: 次の一手の入力欄を出さず、必須を外す【着】。

#### 6.6.7 逃避ログ（`#/escape/new`）

すべて任意。全項目が空でも保存できる【着】。

- 「直前の状態は?」チップ: 不安・疲れ・あいまい・退屈（`priorState`）
- 「どこへ?」チップ: 動画・SNS（`video`）・ゲーム・寝る・その他
- 「楽しかった?」チップ: はい・いいえ・少し
- 関連するやること（任意、今日と昨日のやることのチップ）
- ボタン: 「記録する」（主）、「とばす」（ghost）。どちらもホームへ。

放置セッションから促された場合は、シートの冒頭に「10分タイマーが途中で止まっていました」と書き、`sessionId` を入れて保存する。

#### 6.6.8 1日のしめ（`#/daily`、3問のレッスン）

| 問い | 入力 | 検証 |
|---|---|---|
| 気がかりな、終わっていないことはある? | はい／いいえ（`autoAdvance`） | 必須 |
| 今日、動画・SNS・ゲームに使った時間は? | `NumberStepper`（分）。補足「スクリーンタイムの数字を写す」。チップ 0・30・60・120・180 | 0〜1440 の整数 |
| 今日、予定していたやることはあった? | はい／いいえ | 必須 |

同じ論理日に2回答えたら上書きする【着】。

### 6.7 盤面モジュール【盤】

#### 6.7.1 盤面（`#/board`）

上から:

1. **評価関数カード**: 指標（`h2`）、避けたいこと（最大3つのチップ）、期間と残り日数。未設定なら「評価関数を決める」ボタン。
2. **判定待ち**（段モジュール）: 判定待ちの段の一覧 → 判定へ。
3. **足踏み**（段モジュール）: 却下されていない StallFlag。規則の説明（例: 「期限を3回延ばしています」）と「段を見る」「却下」。
4. **期限リスト**: `buildBoard` の結果（BoardItem の `deadline`／`event` と、OPEN の段の期限を合成）。期限の近い順、期限なしは末尾。各行に「あと{n}日」「今日」「{n}日超過」。段の行には「段」のラベル。
5. **進行中の案件**（`project`）と**資源**（`resource`）。
6. 右上に「追加」。

各 BoardItem の行のメニュー: 「10分だけ手をつける」（`#/tasks/new?boardItemId=…`、D18）、「済みにする」、「編集」、「削除」（取り消しスナックバー付き）。

#### 6.7.2 評価関数（`#/settings/evaluation`）

- 指標（1〜100文字）。入力欄の下に案内「週単位で測れる形になっていますか。例: 週に書いた章数、週の睡眠時間」【盤】。
- 避けたいこと（最大3つ。4つ目の入力欄は出さない）。
- 期間（既定は今日から3か月）。
- 保存時に期間が既存と重なれば「期間が、すでにある評価関数と重なっています」（`PERIOD_OVERLAP`）。
- 過去の評価関数の一覧（読み取りのみ）。

#### 6.7.3 手番トリガー（`#/settings/triggers`）

- 一覧（条件文、有効トグル）。例のチップ: 「5,000円以上の支出」「半日以上の予定」「誘いへの返事」。
- 有効なものが5件あるときに6件目を有効にしようとすると「有効にできるのは5つまでです」（`LIMIT_EXCEEDED`）【盤】。

#### 6.7.4 読みシート（`#/moves/new`、4ステップのレッスン）

全ステップの上部に、有効な評価関数の指標を細い帯で常に表示する【盤】。

| ステップ | 問い | 入力 | 検証・振る舞い |
|---|---|---|---|
| 1 局面 | 「どんな局面?」 | `situation`（1行）。トリガーのチップ（有効なトリガー＋「トリガー外」） | 1〜200文字、必須 |
| 2 候補手 | 「指せる手は?」 | 候補カード2枚（最初から表示）。「候補を足す」で3枚目（4枚目は足せない）。各カードは `description` と、折りたたみ「先を読む」（1手後、2手後、評価関数に照らした点数 `ScoreInput`） | 候補の `description` 2件以上が埋まるまで主ボタン無効 |
| 3 確認 | 「戻せない手はある?」 | トグル「戻せない手がある」（`irreversible`）、トグル「先が読めない」（`unreadable`） | `irreversible` をオンにすると「保留できないか」の注意カード。`unreadable` をオンにすると定跡カード（有効な定跡を最大5件、初期定跡3つが先頭） |
| 4 指す | 「どれを指す?」 | 候補のカードから1つ選ぶ | 主ボタン「これにする」で決定まで終える。「あとで決める」（ghost）なら未決定で保存し、ホームの「決めかけの手」ノードになる |

- 必須項目は局面と候補2件の `description` だけ。最短30秒で保存できる【盤】。
- ステップ3を終えた時点で Move と候補を1トランザクションで保存する（`createMove`）。ステップ4は `decideMove`。

#### 6.7.5 簡易記録（`#/moves/quick`）

- 「どんな局面だった?」（`situation`、必須）
- 「どうした?」（`chosenText`、1〜200文字、必須）
- トグル「あとから記録している（読むべきだった）」（`retro`。`?retro=1` で来たら既定オン）
- 保存すると `mode='quick'`、`decidedAt=now` で記録する。

実験の盤面プリセットのベースライン（A 条件）中は、＋ の「手番」がこの画面に直接遷移する（D31）。

#### 6.7.6 手を決める（`#/moves/:id`）

局面、候補カード（1手後・2手後・点数を展開表示）、主ボタン「これにする」。決定すると `decidedAt` を記録し、`FeedbackSheet` のあとホームに戻る【盤】。

#### 6.7.7 定跡（`#/library/joseki`）

- 一覧。初期定跡3つ【盤】: 「戻せない手は保留する」「選択肢が増える手を優先する」「迷ったら評価関数に近い手を選ぶ」。
- 追加・編集・非表示（削除の代わり）。感想戦から昇格したものには「{日付}の感想戦から」と元の手へのリンク。

### 6.8 段モジュール【刻】

#### 6.8.1 段の登録（`#/goals/new`、5ステップのレッスン）

途中保存はしない。5項目がすべて埋まるまで保存できない【刻】。

| ステップ | 問い | 入力 | 検証 |
|---|---|---|---|
| 1 指標 | 「何で測る?」 | 既存の指標のチップ、または「新しい指標」（名前、単位、向き「多いほど良い／少ないほど良い」、取得方法、「外から確かめられる指標」チェック）。画面下に注記「就職活動や研究成果のように、試行回数が少なく運の影響が大きいことは、結果だけで実力を測れません」 | 指標は数値。取得方法が空なら保存不可 |
| 2 段 | 「どこまで届かせる?」 | 段の名前、閾値、比較（向きから自動で `GTE`／`LTE` を選ぶ。変更可）。プレビュー「{指標}が {値}{単位} 以上」 | 名前 1〜80文字、閾値は数値 |
| 3 期限 | 「いつ確かめる?」 | `DateChips` | 期限は明日以降（D41）。期限なしの経路はない |
| 4 決めておくこと | 「結果を見る前に決めておく」 | 「届いたら、次に何をする?」（`ON_MET`）、「届かなかったら、次に何をする?」（`ON_UNMET`）。どちらも必須。補足「『もう少し続ける』ではなく、具体的な行動を書く」 | 各1〜80文字 |
| 5 予想 | 「どうなると思う?」 | 届く確率（0〜100、10刻みのチップ）、予想する値（数値） | 両方必須 |

確認画面: 「{期限} に、{指標}が {値}{単位} 以上かを確かめる」。主ボタン「この段を立てる」。保存は Goal、Commitment 2件、Prediction 1件、台帳を1トランザクションで行う。

#### 6.8.2 段の詳細（`#/goals/:id`）

- 段の文（指標・閾値・期限）、状態（判定前／届いた／届かなかった）、残り日数。
- 階段（木）: 最上位の段から子へのインデント表示。深さが5を超える段には「最上位から{n}段下」を併記する【刻】。
- 決めておいたこと（2件）、予想、実測の履歴（この指標の Measurement）、延長の履歴、足踏みフラグ、判定（あれば）と訂正の履歴、追跡の選択（刻む／切り直す／取り下げる）。
- ボタン: 判定前で期限内なら「期限を延ばす」、判定待ちなら「判定する」、届かなかった段なら「刻む」「切り直す」（追跡の選択をしていない場合）。
- 段の削除はない。最上位の段以外は「非表示」にできる（`hiddenAt`）【刻】。

#### 6.8.3 実測を記録（`#/measure/new`）

指標のチップ、値、日時（既定は今）、メモ（任意）。保存すると取り消しはできない（追記専用）ので、主ボタンを「確かめる」→ `CheckSheet`「この値で記録します。あとから変更はできません」→「記録する」の2段にする。

#### 6.8.4 判定（`#/judge/:goalId`、レッスン）

この画面が最も避けられやすい。入力を1分以内に終わる構造にする【刻】。

| ステップ | 中身 |
|---|---|
| 1 | **決めておいたこと**のカード（届いたら／届かなかったら）を最上部に表示。その下に「実測は?」の数値入力（DOM 上もカードの後に置く）。参考として「最新の実測: 12（10/15）」を小さく出す（入力欄には初期値を入れない）。主ボタン「確かめる」 |
| 2 | `CheckSheet`: 「{値}{単位}。{閾値}{単位} 以上に 届いた／届かなかった」（結果は計算で出す。クライアントから結果を選ばせない）。注記「確定すると変更できません。訂正は追記で残ります」。「確定する」「入力を直す」 |
| 3（届かなかった場合） | 「かけた時間は?」（時間、数値）、「失ったものは?」（`costNote`、1〜200文字）。どちらも必須 |
| 4（届かなかった場合） | 「次はどうする?」3つのボタンを同じ見た目で並べる: 「刻む」「切り直す」「取り下げる」。選択は必須で、保留はできない【刻】 |
| 完了 | `FeedbackSheet`「判定を記録しました」。続けて、該当する「決めておいた次の行動」を表示する。届いた場合は「次の段を立てる」「あとで」、刻む・切り直すを選んだ場合はそのレッスンへ |

- **届いた／届かなかったで、色・音・動き・コマの有無を変えない**（§2.2）。
- 判定要求からの経過時間は `requestedAt` と `judgedAt` から計算できるので、画面では表示しない。

#### 6.8.5 刻む・切り直す（`#/goals/:id/kizami`、`#/goals/:id/recut`）

- 段の登録と同じ5ステップ。上部に親（または元の段）の情報を常に表示する。指標は親と同じものを初期値にする。
- 刻む: 新しい段の `parentId` = 元の段。切り直す: `parentId` = 元の段の親、`recutOfId` = 元の段。
- 元の段の状態は `UNMET` のまま変えない【刻】。
- 元の段が `OPEN` の場合は、どちらの画面にも入れない（`CONFLICT`）。

#### 6.8.6 期限の延長（`#/goals/:id/extend`）

新しい期限（今の期限より後）と理由（1〜200文字、必須）。期限日を過ぎた段には出さない（D34）。延長は Goal の期限の更新と DeadlineExtension の追記を1トランザクションで行う【刻】。

#### 6.8.7 較正（`#/review/calibration`）

助言や評価の言葉は表示しない【刻】。

- 主指標: 正規化した符号付き誤差の平均（§8.8.1）。大きな数字と「＋なら予想が実測より高め、−なら低め」の説明。
- `CalibrationChart`: 判定ごとの正規化誤差の時系列（ゼロ線の上下で過大・過小を分ける）。
- 散布図: 直近20件の「予想 ÷ 閾値」と「実測 ÷ 閾値」、対角線つき。
- 確率の較正: 「予想した確率の平均 {p}%／実際に届いた割合 {q}%（{n}件）」。
- 感情予想の誤差: 強さと持続の、予想−実際の平均と件数。
- 判定遅延の中央値（時間）。
- 指標ごとの生の差の一覧（単位つき）。

予想のない判定は除外する【刻】。

#### 6.8.8 判定の履歴（`#/library/history`）

未達も含む全判定を新しい順に表示する。削除はできず、絞り込み（届いた／届かなかった、指標）だけできる【刻】。各行から訂正を追記できる（「値の訂正」「記述の訂正」、理由必須）。

### 6.9 週次ふりかえり（`#/review/weekly/:weekStart`）

1本のレッスンに、元の3つの振り返りをまとめる（D20）。1枚ずつ進み、**1枚ごとに即保存**する。途中で閉じても、次に開くと続きから始まる。上部のステップ表示はカードの総数で分割する。

### 6.10 ふりかえりタブ（`#/review`）

- 最上部: 今週のふりかえりの入口カード（未完了なら主ボタン「始める」、完了なら「記録済み」と「見直す」）。過去の週の一覧（週の選択）。

### 7.5 台帳（ハッシュ連鎖）【統】D5

追記専用テーブルの改ざんを「検出できる」状態にする仕組み。

- ハッシュ関数: SHA-256（`@noble/hashes/sha256`。同期で動くので Dexie のトランザクション内で使える）。
- 正規化: `canonicalJSON(record)` はキーを辞書順に並べ、空白なしで直列化する。`undefined` のキーは出力しない。
- 計算: `hash = hex(sha256(prevHash + '|' + table + '|' + canonicalJSON(record)))`。最初のエントリの `prevHash` は `'0'.repeat(64)`。
- 追記: 追記専用テーブルへの `add` は、必ずリポジトリ関数 `appendImmutable(table, record)` を通す。同じ `rw` トランザクション内で、`ledger` の最後のエントリを読み、ハッシュを計算して `ledger` に追加する。
- 検証 `verifyLedger(entries, recordsByTable)`（純粋関数）:
  1. `seq` 順に `prevHash` が前のエントリの `hash` と一致するか。
  2. 各エントリについて、現在のレコードからハッシュを再計算して一致するか。
  3. レコードが存在しない、または台帳に載っていないレコードがないか。
  4. 結果は `{ ok: true, count } | { ok: false, table, seq, reason }`。
- 実行時期: 起動後のアイドル時（`requestIdleCallback`）、設定画面の「確認する」、インポートの前。
- 失敗時: 割り込みカード4と設定画面に表示する。**アプリは止めない**（記録を続けられることを優先する）。
- 全データ削除は `db.delete()` でデータベースごと破棄する（フックを通らない。D6）。
- インポートは、ファイル内の台帳とレコードで `verifyLedger` を通し、通らなければ拒否する（D7）。通ったら `db.delete()` → 再オープン → 1トランザクションで `bulkAdd`。

#### 8.2.5 傾向（`patterns.ts`）

`detectPatterns(habit, logs, today)`:

2. 全体の割合 `overall = done 日数 / 対象日数`。

### 8.8 較正（`domain/goals/calibration.ts`）【刻】D37

#### 8.8.1 正規化した符号付き誤差

判定 `j`（予想がある段だけ）について:

- `p` = その段の OUTCOME 予想の `value`（複数あれば期限前で最も新しいもの）
- `a` = `effectiveValue(j, corrections, 'actualValue')`
- `s` = 指標の向きが `HIGHER_IS_BETTER` なら `+1`、`LOWER_IS_BETTER` なら `−1`
- `raw = s × (p − a)`（指標の単位のまま）
- `norm = raw / max(|targetValue|, 1)`

$$E_{cal} = \frac{1}{n}\sum_{i=1}^{n} norm_i$$

正なら、予想が実測より良い側にずれている（自己評価が高め）。負なら低め。**符号を残すのが要点**で、絶対値だけでは過大評価か過小評価かが消える【刻】。

- `sound`・`haptic`・`variant` は、イベントの種類にも結果にも依存しない定数。
- `copyKey` はイベントの種類で決まる（例: `judgment` → `feedback.judgmentRecorded`）。**`outcome` や `rating` で変えない。**
- テスト（`AC-UX-04`）: `feedbackFor({type:'judgment', outcome:'MET'})` と `feedbackFor({type:'judgment', outcome:'UNMET'})` が深い等価。`moveReview` の `good` と `bad` も同様。`habitDone` と `habitMissed` の `sound`・`haptic`・`variant` が同じ。

### 8.12 入出力の補助

#### 8.12.1 `.ics` の書き出し（`domain/ics.ts`）

- `exportHabitIcs(habit)`: `schedule.time` がある習慣について、`RRULE:FREQ=WEEKLY;BYDAY=…` 付きの VEVENT を返す。`time` がなければ `null`【仕】。`DTEND` は単位が「分」なら `DTSTART + amount 分`、それ以外は `DTSTART + 15分`【統】。
- `exportWeeklyReviewIcs(settings)`: `weeklyReviewIcs` の曜日と時刻に毎週の VEVENT（タイトル「一手 週次ふりかえり」）。
- `exportGoalDeadlinesIcs(goals)`: `OPEN` の段の期限を終日の VEVENT（`DTSTART;VALUE=DATE`）で。
- 時刻はフローティング（`Z` なし、TZID なし）で書く。改行は CRLF。`UID` は `<レコードID>@itte`。
- 本文に禁止語を入れない。リマインダー（`VALARM`）は付けない（催促しない。§2.3-5）。

#### 8.12.2 `.ics` の読み込み（`parseIcs(text, today)`）

- 行の折り返しを戻し、`VEVENT` の `UID`・`SUMMARY`・`DTSTART`（`DATE` と `DATE-TIME` の両方）を読む。
- `today`〜`today+60` に始まる予定だけを返す。`RRULE` は展開しない（最初の1回だけ）。
- 取り込みは `type='event'`, `source='ics'`, `externalUid=UID`。

#### 8.12.3 CSV（`domain/csv.ts`）

- 1テーブル1ファイル、BOM 付き UTF-8、CRLF【着】。
- `EpochMs` の列は ISO 8601（`toISOString()`）に変換。`LocalDate` はそのまま。配列とオブジェクトは JSON 文字列。
- `"`、`,`、改行を含む値はダブルクォートで囲み、`"` は `""` にする。
- zip は `fflate` の `zipSync` で作る。ファイル名 `itte-csv-YYYYMMDD.zip`。

## 9. 実験と検証

このアプリが効いたかどうかを、使用感ではなく数値で判定する。設計時点で反証条件を決めておかないと、作った本人が「役に立った気がする」で終わらせる【刻】。

### 9.1 統合の考え方 D15

- 3つの元設計書は、それぞれ別の自己実験（ABAB など）を持っていた。同時に走らせると条件の切り替えが互いに交絡するので、**実験は同時に1つだけ**実行できる（I17）。
- 実行中でないモジュールは、常にすべての機能が有効（B 条件）。
- 実験の条件は、記録の作成時にレコードへ保存する（`Session.roughMode`、`Move.phase`、`Judgment.enforced`）。あとから開始日を変えても過去の記録の条件は変わらない。
- 逃避ログ、1日のしめ、習慣の記録は、実験の条件に関係なく常に記録できる【着】。
- 推奨の実施順: ① 着手（4週）→ ② 盤面（10週）→ ③ 段（12週）。頻度の高いモジュールから始めると、早くデータがたまる。

### 9.2 プリセットと機能フラグ（`domain/experiment.ts`）

```ts
export interface Flags {
  experimentId: ID | null;
  preset: ExperimentPreset | null;
  week: number | null;           // 開始日からの経過週（0始まり）
  phase: Phase | null;           // 実験中でなければ null
  roughStart: boolean;           // 着手: ラフ登録の2項目、詰まりボタン、次の一手
  readingSheet: boolean;         // 盤面: 読みシート（false なら簡易記録だけ）
  judgmentEnforced: boolean;     // 段: 判定待ちをホームと盤面に出す
}
export function phaseFor(preset: ExperimentPreset, startDate: LocalDate, today: LocalDate): Phase | 'done' | 'notStarted';
export function computeFlags(experiments: Experiment[], today: LocalDate): Flags;
```

`week = floor(diffDays(today, startDate) / 7)`。

| プリセット | 長さ | 週ごとの条件 | A 条件で変わること | 由来 |
|---|---|---|---|---|
| `start` | 4週 | w0=A, w1=B, w2=A, w3=B | `roughStart=false`: ラフ登録は `title` だけ。詰まりボタン、`firstAction` の表示、次の一手の入力と表示を隠す。`Session.roughMode=false` | 【着】 |
| `board` | 10週 | w0〜1=A（ベースライン）, w2〜9=B | `readingSheet=false`: ＋ の「手番」が簡易記録になる。週次の感想戦は行う | 【盤】 |
| `kizami` | 12週 | w0〜1=A, w2〜5=B, w6〜7=A, w8〜11=B | `judgmentEnforced=false`: 判定待ちをホームと盤面に出さない（段の詳細からは判定できる）。実測と予想の記録は続ける | 【刻】 |

### 9.4 仮説と反証条件（`domain/verify/hypotheses.ts`）

各仮説の判定関数は `{ status, detail }` を返す。`status` は `running`（実験中）／`insufficient`（データ不足）／`supported`（支持）／`falsified`（反証）／`undetermined`（判定不能）。閾値は `domain/verify/thresholds.ts` の定数にまとめる。

#### 着手プリセット【着】

| ID | 仮説 | 指標 | 支持 | 反証 | データ不足の条件 |
|---|---|---|---|---|---|
| H1 | 初日に止まる原因は完璧主義の予測 | 着手率（A 週 vs B 週） | w1−w0 と w3−w2 がどちらも +0.20 以上 | どちらか一方でも +0.20 未満 | いずれかの週で「やること×予定日」が3組未満 |
| H2 | 行動は回避駆動 | 逃避ログの `priorState` と `enjoyed` | 記入済みのうち「不安」が過半数、かつ「楽しくない」が過半数 | 「退屈」か「疲れ」が最多、または「楽しい」が過半数 | 記入済みが5件未満。**逃避ログの記録率が50%未満なら `undetermined`**（記録漏れ自体が回避の一部かもしれないので、記録率も数値で残す） |
| H3 | 詰まり点の言語化で離脱が減る | B 週の `stuckContinueRate` vs `noStuckContinueRate` | 前者が後者より 0.10 以上高い | 差が 0.10 未満 | どちらかの分母が5件未満 |
| U1 | 課題のない日の漂流（未解決） | `driftByWorry` | 気がかりのない日の中央値が、ある日より15分以上少ない →「背景不安説」 | 差が15分未満 →「既定値説」 | どちらかが5日未満 |

> H3 の 0.10 と U1 の15分は元設計書に数値がないため、この統合で暫定的に決めた（§15-6）。

#### 盤面プリセット【盤】

検証する仮説:「生活で先が読めないボトルネックは、読みの力ではなく、手番への気づきと盤面の可視化である」。

| ID | 指標 | 支持 | 反証（こうなれば仮説または設計が誤り） | データ不足 |
|---|---|---|---|---|
| B1 | 悪手率（ベースライン w0〜1 vs B 期間の最後の4週 w6〜9） | B が A より低い | B が A 以上 → アプリに効果なし | どちらかの感想戦が5件未満 |
| B2 | 見落としの内訳（B 期間） | 「読み違い」以外が最多 | 「読み違い」が最多 → ボトルネックは気づきではなく読みの力。設計を見直す | 悪手が3件未満 |
| B3 | 事後の気づき（あとから記録の件数、B 期間の前半4週 vs 後半4週） | 後半が前半より少ない | 減らない → トリガーの定義が機能していない | 前半が0件 |
| B4 | 継続率（週次ふりかえりを完了した週の割合、全期間） | 50%以上 | 50%未満 → 入力負荷が高すぎる | ― |

#### 段プリセット【刻】

| ID | 指標 | 反証条件 | 反証されたときに先に疑うもの |
|---|---|---|---|
| K1 | 較正誤差の絶対値（B1 期間 w2〜5 vs B2 期間 w8〜11 の `|E_cal|`） | 減少しない | 指標の設定粒度 |
| K2 | 判定遅延の中央値（同上） | 増加する（記録の不可逆性が回避を強めている） | 原則 U6（不可逆性） |
| K3 | 使用率（B1 期間） | 50%を下回る（続かないものは効果を持ちえない） | 入力コスト |
| K4 | 刻み発生率（B1 期間 vs B2 期間） | 変化しない（足踏みフラグの提示後も刻みが増えない） | 足踏みの定義 |

主要指標は K1 と K2。ほかは補助で、単独では成功の根拠にしない【刻】。データ不足の条件は、各期間の判定が3件未満。

#### 限界（画面にも1行で出す）

- 悪手かどうか、実測値の多くは自己申告で、甘くなりうる。判断の妥当性と結果を別欄にすることで、結果に引きずられる分だけは減らす【盤】【刻】。
- n=1 の個人内時系列なので、有意差検定は使わず、傾向と反転の有無で判断する【刻】。
- 作者自身で検証すると、設計意図を知っているぶん効果が過大に出る【刻】。

### 9.5 実験画面（`#/review/experiment`）

- 実行中でなければ: プリセットのカード3枚（名前、長さ、A 条件で変わること、検証する仮説）。開始日（既定は次の月曜）を選んで「この実験を始める」。
- 実行中なら: 週の帯（A／B の区画を並べ、今週に印）、現在の条件の説明（例: 「いまは A（比較のための期間）。ラフ登録は名前だけになります」）、仮説ごとの状態の表、「中止する」（確認シート1段）。
- 終了した実験の一覧と、各仮説の最終判定。
- 判定の表示は事実だけ（例: 「H1 反証: w1−w0 = +0.25、w3−w2 = +0.08」）。褒める・慰める文言は出さない。

ESLint で強制する:

- `src/ui/**` から `src/db/db` の直接 import を禁止（リポジトリとクエリを通す）。
- `src/ui/**` で日本語の文字列リテラルを JSX に直接書くことを禁止（`src/copy/ja.ts` を通す。`no-restricted-syntax` で `JSXText` に `/[぀-ヿ一-龯]/` を含むものを禁止）。

### 11.6 時刻の扱い（UI）

- `useNow(intervalMs)`: 現在時刻を返すフック。タイマー画面は1000ms、ほかは60000ms。`visibilitychange` で即時更新する。
- `useToday()`: `logicalDate(now)`。論理日が変わったら（4:00 をまたいだら）再描画する。
- テストでは `vi.setSystemTime`（Vitest）と `page.clock`（Playwright）で時刻を固定する。

## 14. デプロイ

GitHub Pages に静的配置する【仕】。

- リポジトリ名の既定は `itte`。URL は `https://eguchi-kd.github.io/itte/`。
- `vite.config.ts` の `base` は `process.env.VITE_BASE ?? '/itte/'`。別のリポジトリ名にする場合は環境変数で変える。
- HashRouter なので `404.html` のリダイレクトは不要（D25）。
- 同じ `github.io` のオリジンにある他のアプリと IndexedDB の名前空間を共有するので、DB 名を `itte` で固定する（衝突を避ける）。

`.github/workflows/deploy.yml`:

```yaml
name: Deploy to GitHub Pages
on:
  push:
    branches: [main]
permissions:
  contents: read
  pages: write
  id-token: write
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npm run lint && npm run typecheck && npm run test
      - run: npm run build
      - uses: actions/configure-pages@v5
      - uses: actions/upload-pages-artifact@v3
        with: { path: dist }
  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
    steps:
      - uses: actions/deploy-pages@v4
```

## 15. 未解決の論点

ここに挙がっている点は、実装者が勝手に決めない。該当箇所に `// TODO(spec): 15-<番号>` を残し、`docs/questions.md` に書いて報告する。暫定値で動かす必要がある場合は、`domain/verify/thresholds.ts` などの定数1か所に置く。

1. **不可逆性の強度**【刻】: 削除不可は正確さを守るが、回避を増やす可能性がある。どちらが支配的かは実測するまで分からない。最初は不可逆で始め、K2（判定遅延）が反証されたら緩める（例: 非表示を許す範囲を広げる）。
2. **指標の粒度を誰が決めるか**【刻】: 自己認識が歪んでいる人が、自分で適正な段を設定できるなら、そもそもこのアプリは要らない。初期の段だけ外部の基準（過去の実績の分布、資格や試験の級）に依存させる案がある。
3. **感情予想が内省を過剰にしないか**【刻】: 苦痛を数値化すること自体が、苦痛への注意を増やす可能性がある。D36 で「段ごとに1日1回まで」にしたが、頻度は実測で見直す。
4. **単一ユーザー検証の外的妥当性**【刻】: 最低1名、設計を知らない利用者で再現を見たい。現在の構成（端末内のみ）では、その人の端末に入れてもらい、書き出しを受け取る形になる。
5. **課題のない日の漂流**【着】: 「背景にある未完了課題の不安」と「外部構造がないと低負荷行動に落ちる既定値」のどちらか。U1 で判定する。
6. **この統合で決めた暫定値**: H3 の差 0.10、U1 の差15分、量を上げる提案の式（§8.2.3）、傾向は全体より低いものだけ（§8.2.5）、`.ics` の `DTEND` の15分（§8.12.1）、週次ふりかえりの表示期間（D21）。どれも元設計書に数値がなかった。
7. **実験の交絡**: 実験を1つに絞っても、ほかのモジュール（例: 常に有効な習慣）が同時に効いている可能性は残る。n=1 の時系列ではこれを完全には分けられない。
8. **ゲーミフィケーションそのものの検証**（D11）: 将来「ストリークは本当に回避を増やすのか」を確かめたくなった場合は、実験ランナーのプリセットとして、反証条件を先に決めたうえで追加する。v1 では実装しない。
9. **端末間の同期**【着】【刻】: PC とスマホの間で同期が必要になった場合だけ、Supabase などを検討する。v1 の範囲外。
10. **適用範囲の限界**【刻】: 試行回数が少なく運の寄与が大きい領域（就職活動、研究成果）で、結果を実力の推定量として使うのは誤り。登録画面の注記（§6.8.1）以上の制御はしていない。
